# 최신 소스 병합 체크리스트 및 설계안 (2026-07-04)

## 1) 목표

- ref-source-code의 최신 기능 코드를 우선 반영한다.
- 쿠버네티스 운영 안정성(마이그레이션/시크릿/이미지 정책)은 현재 정책을 유지한다.
- DB 스키마 단일 진실원(Single Source of Truth)을 Alembic으로 정렬한다.

## 2) 병합 원칙

- 기능 로직: 최신(ref) 우선.
- 배포 자산: 현재(main) 우선.
- DB 변경: 애플리케이션 런타임 DDL보다 Alembic 리비전으로 관리.
- 위험 변경은 단계별 릴리즈(스키마 -> 백엔드 -> 프론트)로 분리.

## 3) 범위 분류

### A. 최신(ref) 우선 채택

- 백엔드 비즈니스 로직(라우터/서비스/스케줄러 파이프라인)
- 프론트 화면/훅/서비스
- CSV 동기화 개선 로직

### B. 현재(main) 유지

- 쿠버네티스 매니페스트 전체(Deployments/Jobs/Secrets/ConfigMaps/NetworkPolicy)
- 운영형 프론트 컨테이너 실행 방식(빌드 산출물 기반)
- DB_AUTO_CREATE_TABLES=false 운영 정책

### C. 수동 머지 필수

- 설정/부팅: config, main
- DB: schema.sql, seed.sql, Alembic baseline/추가 리비전
- 문서 업서트 제약(Unique + on conflict)

## 5) 설계안 (의사결정)

### 설계안 D1: DB 단일 진실원

결정:

- Alembic을 유일한 스키마 변경 경로로 사용.

근거:

- 런타임 DDL(create_all/ALTER)은 환경별 드리프트 유발 가능성이 높음.

적용:

- 운영 배포에서 DB_AUTO_CREATE_TABLES=false 유지.
- 앱 시작 시 스키마 변경 SQL 실행은 제거 또는 개발 환경 한정.

### 설계안 D2: API 하위호환 브릿지

결정:

- 내부 저장 컬럼은 product_category로 통일하되, 외부 응답 필드는 필요 시 task_type 별칭 제공.

근거:

- 프론트/외부 연동 코드 급격한 동시 수정 리스크 감소.

적용:

- 변환 계층(Serializer/Response Mapper)에서 단일 관리.

### 설계안 D3: 문서 업서트 무결성

결정:

- documents(uploader, file_path) 유니크 제약 + upsert 표준화.

근거:

- 중복 업로드/경합 업데이트 시 데이터 정합성 향상.

적용:

- DB 제약 적용 후 서비스 on_conflict_do_update 사용.

### 설계안 D4: 배포 분리 전략

결정:

- 코드 병합과 K8s 운영 변경을 분리 배포.

근거:

- 장애 원인 분리와 롤백 속도 개선.

적용:

- 1차: DB + backend
- 2차: frontend
- 3차: 모니터링/정책 미세조정
