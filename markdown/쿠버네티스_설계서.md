# 쿠버네티스 전환 설계서

**대상:** manufacturing-scheduler-sub
**작성 목적:** Docker Compose 기반 구성을 Kubernetes로 옮기기 위한 설계 기준 정리
**설계 원칙:** 초보자도 이해하기 쉬운 구조, 주석이 많은 단순한 YAML, 운영과 개발을 섞지 않기

---

## 1. 설계 방향 요약

이 프로젝트는 다음처럼 나누어 생각하면 가장 이해하기 쉽다.

- 외부 진입점은 `Ingress` 하나로 통일한다.
- 실제 앱은 `manufacturing-app` 과 `manufacturing-monitoring` 으로 나누고, Ingress Controller 는 `ingress-nginx` 네임스페이스에 둔다.
- 비밀값은 `Secret`, 일반 설정값은 `ConfigMap` 으로 분리한다.
- 데이터가 필요한 PostgreSQL은 `StatefulSet` + `PVC` 로 운영한다.
- 화면과 API 서버는 `Deployment` + `Service` 로 운영한다.
- 로컬 3대 VM 클러스터에서는 `MetalLB` 가 외부 IP를 제공하고, `ingress-nginx` 가 라우팅을 담당한다.

핵심은 Docker Compose 의 서비스 목록을 Kubernetes 자원으로 옮기되, 상태 저장과 상태 없음만 구분하는 것이다.

## 2. base 폴더가 꼭 필요한가?

결론부터 말하면, 이번 단계에서는 `base` 폴더가 없어도 된다.

이유는 다음과 같다.

- 아직은 단일 목적의 로컬 VM 클러스터만 목표다.
- 환경 분기(dev/prod/stage)가 복잡하지 않다.
- 초보자에게는 `deployments/`, `secrets/`, `configmaps/` 처럼 기능별 폴더가 더 직관적이다.
- `base` + `overlay` 구조는 강력하지만, 처음 배우는 입장에서는 파일이 너무 분산되어 오히려 헷갈릴 수 있다.

따라서 첫 버전은 다음처럼 단순하게 시작하는 것을 권장한다.

```text
deployments/
├── configmaps/
├── secrets/
├── postgres/
├── backend/
├── frontend/
├── ingress/
├── jobs/
└── monitoring/
```

나중에 환경이 늘어나면 그때 `base` 를 추가해도 늦지 않다.

## 3. 추천 폴더 구조

아래 구조는 읽기 쉬움을 우선한 설계다.

```text
deployments/
├── namespace.yaml
├── configmaps/
│   ├── app-config.yaml
│   ├── postgres-config.yaml
│   └── monitoring-config.yaml
├── secrets/
│   ├── app-secrets.yaml
│   ├── postgres-secret.yaml
│   └── r2-secret.yaml
├── postgres/
│   ├── postgres-pvc.yaml
│   ├── postgres-statefulset.yaml
│   └── postgres-service.yaml
├── backend/
│   ├── backend-deployment.yaml
│   ├── backend-service.yaml
│   └── backend-hpa.yaml
├── frontend/
│   ├── frontend-deployment.yaml
│   └── frontend-service.yaml
├── ingress/
│   ├── ingress-nginx-values.yaml
│   └── app-ingress.yaml
├── jobs/
│   ├── migrate-job.yaml
│   └── seed-job.yaml
└── monitoring/
    ├── prometheus-deployment.yaml
    ├── prometheus-service.yaml
    ├── grafana-deployment.yaml
    ├── grafana-service.yaml
    └── monitoring-pvc.yaml
```

### 폴더 역할

- `configmaps/`: 코드가 아닌 설정값 저장
- `secrets/`: 비밀번호, API 키, JWT 시크릿 저장
- `postgres/`: DB 관련 자원만 모음
- `backend/`: FastAPI 서버 관련 자원만 모음
- `frontend/`: Next.js 화면 자원만 모음
- `ingress/`: 외부 진입점과 경로 라우팅 설정
- `jobs/`: 마이그레이션과 초기화 작업
- `monitoring/`: Prometheus, Grafana 같은 관측 도구
- `networkpolicy/`: 네임스페이스 간 통신 제어

### 네임스페이스 배치

- `manufacturing-app`: frontend, backend, postgres, app ingress, app secret/config
- `manufacturing-monitoring`: Prometheus, Grafana, postgres-exporter, monitoring secret/config
- `ingress-nginx`: Ingress Controller 전용 namespace

### 네임스페이스 통신 원칙

- `ingress-nginx` 는 `manufacturing-app` 의 frontend/backend 로만 들어온다.
- `manufacturing-monitoring` 의 Prometheus 는 `manufacturing-app` 의 backend /metrics 를 읽는다.
- `manufacturing-app` 의 backend 는 `manufacturing-app` 의 postgres 에만 접속한다.
- `manufacturing-monitoring` 의 postgres-exporter 는 `manufacturing-app` 의 postgres 에만 접속한다.
- egress 는 아직 제한하지 않고, ingress 만 먼저 잠근다.

### 모니터링 외부 노출 원칙

- Grafana 와 Prometheus 는 `ingress-nginx` 를 통해 외부에서 볼 수 있게 한다.
- Prometheus 는 `/prometheus`, Grafana 는 `/grafana` 경로로 분리한다.
- 내부 통신은 NetworkPolicy 로만 허용한다.

### 모니터링 외부 노출 원칙

- Grafana 와 Prometheus 는 `ingress-nginx` 를 통해 외부에서 볼 수 있게 한다.
- Prometheus 는 `/prometheus`, Grafana 는 `/grafana` 경로로 분리한다.
- 내부 통신은 NetworkPolicy 로만 허용한다.

| Docker Compose 서비스 | Kubernetes 권장 리소스                                                                         | 비고                                   |
| --------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------- |
| db                    | `manufacturing-app` 네임스페이스의 StatefulSet + PVC + Service                                 | 데이터 보존 필요                       |
| backend               | `manufacturing-app` 네임스페이스의 Deployment + Service                                        | 상태 없음                              |

| cadvisor              | 별도 재검토                                                                                    | Kubernetes에서는 그대로 쓰기 어려움    |
| nginx-exporter        | 선택                                                                                           | nginx를 직접 운영할 때만 의미 있음     |
| postgres-exporter     | Deployment + Service                                                                           | DB 메트릭 수집용                       |

## 5. 네트워크 흐름 설계

로컬 3대 VM + MetalLB 환경에서는 다음 흐름을 목표로 한다.

```text
사용자 브라우저
   ↓
MetalLB가 할당한 외부 IP
   ↓
ingress-nginx (LoadBalancer Service)
   ↓
Ingress 규칙
   ├── /        → frontend Service
   └── /api     → backend Service
                ↓
           PostgreSQL Service
```

### 왜 이 구조가 좋은가

- 사용자는 하나의 주소만 기억하면 된다.
- 프론트가 `/api/...` 상대경로를 써도 자연스럽게 동작한다.
- backend와 frontend를 서로 다른 포트로 외부 노출할 필요가 없다.
- DB를 외부에 노출하지 않아도 된다.

## 6. Ingress 설계

이 프로젝트는 경로 기반 라우팅(path-based routing)이 가장 적합하다.

### 권장 규칙

- `/` → frontend
- `/api` → backend

### 장점

- 프론트 코드 변경이 거의 없다.
- 현재 프로젝트의 API 호출 방식과 맞는다.
- 초보자 입장에서 이해하기 쉽다.

### 주의할 점

- `ingress-nginx` 가 먼저 설치되어 있어야 한다.
- MetalLB 가 LoadBalancer IP 를 할당할 수 있어야 한다.
- 나중에 도메인이 생기면 host 기반 규칙도 추가할 수 있다.

## 7. 각 자원별 설계

### 7.1 Namespace

전용 namespace를 하나 둔다.

예: `manufacturing-scheduler`

이유:

- 관련 리소스를 한 번에 모아서 보기 쉽다.
- 나중에 삭제/재배포가 편하다.
- 실수로 다른 프로젝트와 섞이는 것을 막는다.

### 7.2 ConfigMap

비밀이 아닌 설정을 넣는다.

예시 항목:

- `NEXT_PUBLIC_API_URL`
- OpenAI 모델명
- R2 prefix 값
- 업로드 제한 크기
- CORS 허용 도메인

### 7.3 Secret

민감한 값을 넣는다.

예시 항목:

- `POSTGRES_PASSWORD`
- `SECRET_KEY`
- `OPENAI_API_KEY`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`

### 7.4 PostgreSQL

PostgreSQL은 반드시 상태 저장 리소스로 본다.

권장 구성:

- `StatefulSet`
- `PVC`
- `ClusterIP Service`

설계 포인트:

- 데이터는 PVC 에 저장한다.
- Pod 가 재시작되어도 데이터가 사라지면 안 된다.
- 외부 공개는 하지 않는다.

### 7.5 Backend

FastAPI 서버는 `Deployment` 로 둔다.

권장 구성:

- `Deployment`
- `ClusterIP Service`
- `readinessProbe`
- `livenessProbe`

설계 포인트:

- 앱 내부에서 DB, R2, OpenAI 를 사용한다.
- 외부에는 직접 노출하지 않고 Ingress 뒤에 둔다.
- 처음은 replicas 1개로 시작한다.

### 7.6 Frontend

Next.js 서버도 `Deployment` 로 둔다.

권장 구성:

- `Deployment`
- `ClusterIP Service`
- `readinessProbe`

설계 포인트:

- 운영 환경에서는 `next build` 후 `next start` 가 맞다.
- 개발용 `next dev` 는 K8s 운영 배포용으로는 부적절하다.
- 프론트는 `/api` 를 같은 호스트로 호출하므로 Ingress 구조와 잘 맞는다.

### 7.7 Job

초기화나 마이그레이션은 Job 으로 분리한다.

예시:

- DB 마이그레이션 Job
- seed 데이터 Job

이유:

- 앱이 뜰 때마다 자동 실행되면 위험하다.
- 여러 Pod 가 동시에 올라오면 중복 실행 문제가 생길 수 있다.

### 7.8 Monitoring

관측 도구는 앱과 분리한다.

권장 구성:

- Prometheus: 메트릭 수집
- Grafana: 대시보드
- postgres-exporter: DB 상태 수집
- 필요 시 nginx exporter 추가 검토

설계 의도:

- Docker 버전에서 보려 했던 것과 같은 축을 유지한다.
- 생산 데이터, 챗봇 사용량, OpenAI 토큰, 서버 상태를 한 화면에서 본다.
- 다만 Kubernetes 에서는 컨테이너 중심 관찰보다 클러스터 중심 관찰로 한 단계 확장한다.

개선 포인트:

- Grafana 와 Prometheus 는 Ingress 뒤에 노출한다.
- DB 지표와 앱 지표를 분리해서 본다.
- Docker 의 cAdvisor 의존은 Kubernetes 에서는 재검토한다.
- 장기적으로는 `node-exporter` 와 `kube-state-metrics` 를 추가하는 쪽이 더 자연스럽다.
- Grafana 대시보드는 기존 `monitoring/grafana/provisioning` 을 커스텀 Grafana 이미지에 포함시켜 이식한다.

#### Prometheus 외부 접속 설정

- Prometheus Deployment 에 `--web.route-prefix=/prometheus` 와 `--web.external-url=/prometheus` 를 둔다.
- monitoring Ingress 에서 `/prometheus` 경로를 Prometheus Service 로 연결한다.
- Grafana 는 `/grafana` 경로로 노출한다.
- Grafana Deployment 에 `GF_SERVER_ROOT_URL` 과 `GF_SERVER_SERVE_FROM_SUB_PATH=true` 를 둔다.

1차 범위:

- Prometheus
- Grafana
- postgres-exporter
- backend metrics

2차 검토 대상:

- node-exporter
- kube-state-metrics
- nginx exporter
- cAdvisor 대체 여부

## 8. 현재 프로젝트에서 바로 보이는 조정 포인트

이 프로젝트는 그대로 Kubernetes로 옮기기 전에 몇 가지 조정이 필요하다.

### 8.1 backend Dockerfile

현재 backend 이미지는 개발용 실행이다.

- `--reload` 사용 중
- 운영 배포에는 적합하지 않음

Kubernetes 설계에서는 운영 실행 커맨드로 바꾸는 전제를 둔다.

### 8.2 frontend Dockerfile

현재 frontend도 개발용 실행이다.

- `npm run dev` 사용 중
- 운영 배포에서는 `next build` + `next start` 가 더 적절함

### 8.3 앱 시작 시 DB 생성

앱 시작 시 테이블 생성 로직이 있다.

Kubernetes 운영 관점에서는 이 방식보다 Job 기반 마이그레이션이 더 안전하다.

### 8.4 외부 의존성

이 프로젝트는 다음 외부 서비스에 의존한다.

- PostgreSQL
- Cloudflare R2
- OpenAI

따라서 Secret 관리와 네트워크 접근성 확인이 중요하다.

- 나중에 VM 3대 + MetalLB 환경으로 확장하기 쉽다.

원하면 다음 메시지에서 바로 `deployments/` 폴더의 파일명과 역할을 1개씩 확정하면서 설계를 이어가겠다.

## 13. 1차 구현 범위 확정

처음부터 모든 구성요소를 만들 필요는 없다. 초보자 관점에서는 먼저 "웹 화면이 뜨고, API가 연결되고, DB가 유지되는가"만 확인하면 된다.

그래서 1차 구현 범위는 아래 5개만 잡는 것을 권장한다.

1. Namespace
2. PostgreSQL
3. Backend
4. Frontend
5. Ingress

Monitoring, Job, HPA, exporter 들은 2차 이후로 미뤄도 된다.

### 1차 목표

- 브라우저에서 메인 화면 접속 가능
- `/api/health` 정상 응답
- frontend → backend API 호출 가능
- backend → PostgreSQL 연결 가능
- Pod 재시작 후 데이터 유지

```text
│   ├── backend-deployment.yaml
│   └── backend-service.yaml
├── frontend/
│   ├── frontend-deployment.yaml
│   └── frontend-service.yaml
└── ingress/
   └── app-ingress.yaml
```

### 왜 이 정도만 먼저 만드는가

- 파일 수가 적어서 구조를 이해하기 쉽다.
- 로컬 VM 클러스터에서 가장 빨리 확인할 수 있다.
- 설계가 바뀌어도 수정 범위가 작다.

## 15. 리소스 이름 규칙

이름 규칙을 처음부터 고정하면 나중에 헷갈리지 않는다.

- namespace: `manufacturing-scheduler`
- postgres service: `postgres`
- backend service: `backend`
- frontend service: `frontend`
- ingress: `app-ingress`

- app secret: `app-secrets`
- app configmap: `app-config`

### 이름 규칙 원칙

## 16. 각 파일의 역할 정의

### 16.1 namespace.yaml

이 파일은 전체 자원을 담는 상자 역할을 한다.

포함 내용:

- namespace 이름

설계 메모:

- 모든 리소스는 이 namespace 아래에 배치하는 것을 기본으로 한다.

### 16.2 postgres-secret.yaml

PostgreSQL 접속 정보를 저장한다.

포함 내용:

- DB 이름
- DB 사용자명
- DB 비밀번호

설계 메모:

- 비밀번호는 절대 ConfigMap 에 두지 않는다.
- 운영 환경에서는 외부에 노출되지 않게 한다.

권장 키:

- `POSTGRES_DB`
- `POSTGRES_USER`
- `POSTGRES_PASSWORD`

### 16.3 app-secrets.yaml

애플리케이션 서버가 쓰는 민감값을 저장한다.

포함 내용:

- `SECRET_KEY`
- `OPENAI_API_KEY`
- R2 키들

설계 메모:

- backend Pod 에서만 읽을 수 있게 한다.

권장 키:

- `SECRET_KEY`
- `OPENAI_API_KEY`
- `R2_ACCOUNT_ID`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`
- `R2_BUCKET_NAME`
- `R2_ENDPOINT`

### 16.4 app-config.yaml

변경 가능하지만 비밀은 아닌 설정값을 저장한다.

포함 내용:

- `NEXT_PUBLIC_API_URL`
- OpenAI 모델명
- R2 prefix
- 업로드 제한 크기

설계 메모:

- 환경을 바꿔도 코드 수정이 필요 없게 만드는 용도다.

권장 키:

- `NEXT_PUBLIC_API_URL`
- `OPENAI_EMBEDDING_MODEL`
- `OPENAI_CHAT_MODEL`
- `R2_RAG_PREFIX`
- `R2_SAFETY_MANAGE_PREFIX`
- `R2_SCHEDULE_INPUT_PREFIX`
- `R2_SCHEDULE_OUTPUT_PREFIX`
- `MAX_UPLOAD_SIZE_MB`
- `RAG_CHUNK_SIZE`
- `RAG_CHUNK_OVERLAP`
- `RAG_TOP_K`

### 16.5 postgres-pvc.yaml

PostgreSQL 데이터가 저장될 디스크를 정의한다.

설계 메모:

- PVC 가 없으면 Pod 재시작 시 데이터가 사라질 수 있다.
- DB는 반드시 PVC 와 같이 써야 한다.

### 16.6 postgres-statefulset.yaml

PostgreSQL Pod 를 띄우는 정의다.

설계 메모:

- StatefulSet 은 데이터가 중요한 서비스에 사용한다.
- DB 는 순번이 고정되는 구조보다 StatefulSet 이 적합하다.

### 16.7 postgres-service.yaml

backend 가 DB 에 접속할 때 사용하는 내부 주소를 제공한다.

설계 메모:

- 타입은 ClusterIP 로 둔다.
- 외부에 공개하지 않는다.

### 16.8 backend-deployment.yaml

FastAPI 서버를 배포한다.

설계 메모:

- replicas 1 개로 시작한다.
- readiness/liveness probe 를 넣는다.
- DB, R2, OpenAI 환경변수를 주입한다.

주입 방식:

- DB 주소는 backend 환경변수로 넣는다.
- 비밀값은 Secret 을 참조한다.
- 일반 설정값은 ConfigMap 을 참조한다.

### 16.9 backend-service.yaml

backend 를 내부에서 찾을 수 있게 한다.

설계 메모:

- Ingress 가 backend 로 넘길 대상이 된다.

### 16.10 frontend-deployment.yaml

Next.js 서버를 배포한다.

설계 메모:

- 운영 모드로 실행해야 한다.
- API 주소는 Ingress 기준으로 같은 호스트의 `/api` 를 바라보게 한다.

주입 방식:

- `NEXT_PUBLIC_API_URL` 은 ConfigMap 에서 읽는다.
- frontend 는 가능한 한 Secret 을 직접 읽지 않는다.

### 16.11 frontend-service.yaml

frontend 를 내부에서 찾을 수 있게 한다.

설계 메모:

- Ingress 가 `/` 요청을 이 서비스로 전달한다.

### 16.12 app-ingress.yaml

외부 사용자의 요청을 frontend 와 backend 로 나눈다.

설계 메모:

- `/` → frontend
- `/api` → backend

## 17. 초보자용 설계 원칙

이번 K8s 설계는 다음 원칙을 지키면 이해가 쉬워진다.

- 한 파일에는 한 역할만 넣는다.
- 비밀은 Secret, 설정은 ConfigMap 으로 무조건 분리한다.
- 외부에 노출할 서비스는 Ingress 뒤로 보낸다.
- 상태가 있으면 PVC 를 붙인다.
- 처음부터 복잡한 패턴(base/overlay, many environments) 을 넣지 않는다.
- Docker 의 관측 의도는 유지하되, Kubernetes 에서는 클러스터 친화적인 메트릭 수집 방식으로 조금씩 개선한다.

---

## 17.1 Docker 의도와 Kubernetes 개선안의 대응

기존 Docker 버전에서 보려 했던 것은 대략 다음 네 가지다.

- 서비스가 살아 있는가
- 생산/업무 데이터가 잘 쌓이는가
- 챗봇과 OpenAI 사용량이 얼마나 되는가
- 컨테이너 자원 사용량이 과한가

Kubernetes 에서는 이 의도를 유지하되 보이는 대상을 조금 바꾼다.

| Docker 의도                         | Kubernetes 개선안                           | 비고                           |
| ----------------------------------- | ------------------------------------------- | ------------------------------ |
| `cadvisor` 로 컨테이너 상태 확인    | `node-exporter` + `kube-state-metrics` 검토 | 클러스터 관점이 더 자연스럽다  |
| `nginx-exporter` 로 Nginx 상태 확인 | ingress-nginx 메트릭 또는 필요 시 exporter  | Ingress 중심 구조와 맞춘다     |
| `postgres-exporter` 로 DB 상태 확인 | 유지                                        | DB 운영에 여전히 유효하다      |
| Grafana 에서 업무 데이터 시각화     | 유지                                        | 대시보드 의도와 가장 잘 맞는다 |

초보자용 결론:

- "무엇을 보려 했는가"는 그대로 둔다.
- "어떤 수집 방식이 더 맞는가"만 Kubernetes 에 맞게 바꾼다.

## 19. Secret 설계 상세

Secret 은 "비밀값을 담는 상자"다. Kubernetes 에서는 데이터 자체를 숨겨야 하는 값만 Secret 에 넣는다.

### 19.1 Secret 파일을 나누는 기준

이번 프로젝트에서는 Secret 을 2개로 나누는 것이 가장 이해하기 쉽다.

- `postgres-secret.yaml`: PostgreSQL 접속 정보 전용
- `app-secrets.yaml`: backend 가 쓰는 외부 연동 정보 전용

이렇게 나누면 다음 장점이 있다.

- DB 비밀번호와 OpenAI/R2 키를 섞지 않는다.
- 권한 범위를 머릿속에 쉽게 그릴 수 있다.
- 나중에 수정할 때 파일이 덜 복잡하다.

### 19.2 postgres-secret.yaml 설계

포함할 값:

- `POSTGRES_DB`
- `POSTGRES_USER`
- `POSTGRES_PASSWORD`

권장 형태:

- 타입은 `Opaque`
- 개발 초반에는 `stringData` 를 써서 읽기 쉽게 작성
- 나중에 필요하면 `data` 로 바꿔도 된다

초보자용 주석 방향:

- 이 Secret 은 DB 컨테이너가 시작될 때 참조한다.
- backend 는 이 Secret 을 직접 읽는 대신 DB Service 와 접속 정보만 사용한다.

### 19.3 app-secrets.yaml 설계

포함할 값:

- `SECRET_KEY`
- `OPENAI_API_KEY`
- `R2_ACCOUNT_ID`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`
- `R2_BUCKET_NAME`
- `R2_ENDPOINT`

권장 형태:

- 타입은 `Opaque`
- 민감값은 반드시 Secret 에만 둔다
- frontend 에는 넣지 않는다

초보자용 주석 방향:

- backend 는 이 Secret 을 통해 OpenAI 와 R2 를 쓴다.
- 값이 없으면 챗봇, 문서 업로드, R2 동기화 기능이 실패할 수 있다.

### 19.4 Secret 주입 방식

Kubernetes 에서는 Secret 값을 Pod 환경변수로 넣는 방식이 가장 단순하다.

권장 방식:

- `envFrom` 또는 개별 `env` 로 주입
- 중요한 키는 이름을 명시적으로 매핑

초보자 관점에서의 기준:

- 한 번에 많은 값을 넣고 싶으면 `envFrom`
- 어떤 값이 어디서 왔는지 분명히 보이고 싶으면 개별 `env`

### 19.5 Secret 설계의 주의점

- Secret 은 암호화 저장이 아니라 "일반 ConfigMap 보다 더 조심해서 다루는 값"에 가깝다.
- 운영 환경에서는 RBAC 와 네임스페이스 분리를 같이 고려해야 한다.
- Git 에 직접 평문으로 올리면 안 된다.

## 20. ConfigMap 설계 상세

ConfigMap 은 "비밀은 아니지만 환경에 따라 바뀌는 설정값"을 담는다.

### 20.1 app-config.yaml 설계

포함할 값:

- `NEXT_PUBLIC_API_URL`
- `OPENAI_EMBEDDING_MODEL`
- `OPENAI_CHAT_MODEL`
- `R2_RAG_PREFIX`
- `R2_SAFETY_MANAGE_PREFIX`
- `R2_SCHEDULE_INPUT_PREFIX`
- `R2_SCHEDULE_OUTPUT_PREFIX`
- `MAX_UPLOAD_SIZE_MB`
- `RAG_CHUNK_SIZE`
- `RAG_CHUNK_OVERLAP`
- `RAG_TOP_K`

이 값들은 `backend/app/core/config.py` 에 있는 기본 설정과 직접 연결된다.

### 20.2 frontend 와 backend 의 차이

- frontend 는 주로 `NEXT_PUBLIC_API_URL` 만 있으면 된다.
- backend 는 R2 prefix, OpenAI 모델명, 업로드 제한, RAG 설정까지 읽는다.

즉, frontend ConfigMap 은 비교적 가볍고, backend ConfigMap 은 조금 더 많아진다.

### 20.3 ConfigMap 주입 방식

권장 방식:

- backend Deployment 에 `envFrom` 로 ConfigMap 연결
- frontend Deployment 에는 필요한 값만 개별적으로 연결

초보자 기준의 선택:

- 처음에는 `envFrom` 으로 단순하게 시작
- 나중에 값이 많아지면 개별 `env` 로 바꿔도 된다

### 20.4 ConfigMap 설계의 주의점

- 비밀값을 넣으면 안 된다.
- Secret 과 ConfigMap 의 경계를 처음에 분명하게 정해야 한다.
- `NEXT_PUBLIC_` 로 시작하는 값은 브라우저에서도 노출되는 값이므로 비밀이 아니어야 한다.

## 21. PostgreSQL 설계 상세

PostgreSQL 은 이번 프로젝트의 중심 데이터 저장소다. 따라서 가장 먼저 안정적으로 설계해야 한다.

### 21.1 왜 StatefulSet 인가?

DB 는 Pod 가 사라져도 데이터가 유지되어야 한다.

그래서 다음이 필요하다.

- 고정된 저장소
- 재시작 후에도 살아남는 디스크
- 내부 서비스 주소

이 요구를 만족하는 기본형이 StatefulSet 이다.

### 21.2 PostgreSQL 리소스 구성

권장 파일:

- `postgres-pvc.yaml`
- `postgres-statefulset.yaml`
- `postgres-service.yaml`

### 21.3 PVC 설계

PVC 는 PostgreSQL 데이터 디렉터리를 붙잡는 역할을 한다.

포함 개념:

- 저장 용량 요청
- access mode
- storageClassName

초보자용 설명:

- PVC 는 "DB 파일을 담는 디스크 예약표"라고 생각하면 된다.

### 21.4 StatefulSet 설계

StatefulSet 에는 다음이 들어간다.

- PostgreSQL 이미지
- 환경변수
- 볼륨 마운트
- health probe
- PVC 연결

초보자용 주석 방향:

- 컨테이너가 시작될 때 DB 사용자와 비밀번호를 환경변수로 받는다.
- 데이터는 PVC 에 저장된다.
- StatefulSet 은 DB 같은 상태 저장 앱에 맞는다.

### 21.5 Service 설계

DB Service 는 내부 전용이다.

권장 사항:

- Service 타입은 `ClusterIP`
- 이름은 `postgres`
- backend 는 이 이름으로 접속한다

### 21.6 초기화 전략

PostgreSQL 초기화는 두 가지 중 하나로 생각할 수 있다.

1. 이미지 초기화 기능 사용
2. 별도 Job 에서 schema.sql / seed.sql 적용

이번 프로젝트에서는 **Job 방식이 더 안전**하다.

이유:

- 앱 컨테이너 시작과 초기화가 섞이지 않는다.
- 나중에 스키마 변경을 추적하기 쉽다.
- Kubernetes 다운타임 없이 운영 흐름을 분리하기 좋다.

### 21.7 헬스 체크 설계

PostgreSQL 이 살아 있는지 확인하려면 readiness/liveness probe 를 둔다.

초보자용 기준:

- `pg_isready` 를 쓰는 방식이 가장 이해하기 쉽다.
- DB 가 아직 준비되지 않았으면 backend 가 바로 붙지 않게 한다.

## 22. 1차 구현 시 연결 관계

1차 구현에서는 아래 연결 관계만 기억하면 된다.

```text
frontend
   ↓ /api 요청
Ingress
   ↓
backend
   ↓
postgres Service
   ↓
PostgreSQL Pod + PVC
```

그리고 backend 는 다음 Secret / ConfigMap 을 참조한다.

- `app-secrets`
- `app-config`

PostgreSQL 은 다음 Secret 을 참조한다.

- `postgres-secret`

## 24. Backend Deployment 설계 상세

Backend 는 FastAPI 애플리케이션이다. 이 프로젝트에서 backend 는 화면이 아니라 API 를 책임진다.

### 24.1 backend Deployment 의 역할

Backend Deployment 는 다음 일을 한다.

- FastAPI 서버를 실행한다.
- PostgreSQL 에 연결한다.
- R2 와 OpenAI 를 사용한다.
- 문서 업로드, 챗봇, 일정 조회 API 를 제공한다.

### 24.2 운영 실행 명령

현재 backend Dockerfile 은 개발용 reload 모드에 가깝다. Kubernetes 운영 배포에서는 다음 방식이 더 적절하다.

```text
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

설계 메모:

- `--reload` 는 사용하지 않는다.
- 운영 배포에서는 코드 변경이 자동 반영될 필요가 없다.
- Pod 재시작은 Kubernetes 가 담당한다.

### 24.3 backend Deployment 에 들어갈 핵심 항목

포함할 내용:

- 이미지 이름
- replicas
- 컨테이너 포트 8000
- 환경변수 주입
- readinessProbe
- livenessProbe
- 리소스 요청/제한
- volume 이 필요한지 여부

### 24.4 backend 가 사용하는 환경변수

Backend 는 Secret 과 ConfigMap 을 함께 사용한다.

#### Secret 에서 받는 값

- `SECRET_KEY`
- `OPENAI_API_KEY`
- `R2_ACCOUNT_ID`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`
- `R2_BUCKET_NAME`
- `R2_ENDPOINT`

#### ConfigMap 에서 받는 값

- `NEXT_PUBLIC_API_URL` 은 backend 에는 사실상 필요하지 않다.
- 대신 backend 설정 관련 값만 받는다.
- `OPENAI_EMBEDDING_MODEL`
- `OPENAI_CHAT_MODEL`
- `R2_RAG_PREFIX`
- `R2_SAFETY_MANAGE_PREFIX`
- `R2_SCHEDULE_INPUT_PREFIX`
- `R2_SCHEDULE_OUTPUT_PREFIX`
- `MAX_UPLOAD_SIZE_MB`
- `RAG_CHUNK_SIZE`
- `RAG_CHUNK_OVERLAP`
- `RAG_TOP_K`

추가적으로 backend 에 직접 넣는 일반 값:

- `DATABASE_URL`

주의:

- `DATABASE_URL` 은 Secret 안에 둘 수도 있지만, 이번 설계에서는 DB 연결 구조를 보기 쉽게 하기 위해 backend Deployment 에서 조합하는 방식도 고려할 수 있다.
- 초보자용으로는 `postgres` Service 이름과 DB 비밀값을 분리해서 보는 편이 이해가 쉽다.

### 24.5 readinessProbe 설계

readinessProbe 는 "이 Pod 가 요청을 받을 준비가 되었는가"를 판단한다.

권장 엔드포인트:

- `/api/health`

설계 이유:

- 현재 health API 는 DB 연결 상태를 함께 확인한다.
- backend 가 뜨기만 하고 DB 연결이 안 되면 readiness 에서 걸러낼 수 있다.

초보자용 설명:

- readiness 는 트래픽을 받을 준비 여부다.
- 아직 준비되지 않으면 Ingress/Service 가 이 Pod 로 요청을 보내지 않는다.

### 24.6 livenessProbe 설계

livenessProbe 는 "이 Pod 가 죽었는가"를 판단한다.

권장 엔드포인트:

- `/api/health`

설계 이유:

- 같은 health endpoint 를 써도 된다.
- 단, liveness 는 너무 짧게 잡지 않는 것이 좋다.

초보자용 주의점:

- readiness 와 liveness 는 역할이 다르다.
- readiness 는 "받아도 되나", liveness 는 "재시작해야 하나"다.

### 24.7 replicas 설정

1차 구현에서는 replicas 를 1개로 시작한다.

이유:

- 처음부터 여러 개를 띄우면 디버깅이 어려워진다.
- DB, R2, OpenAI 연결부터 먼저 안정화하는 것이 우선이다.
- 이후 HPA 를 붙여도 늦지 않다.

### 24.8 리소스 요청/제한

초기값은 보수적으로 시작한다.

권장 방향:

- requests 는 낮게 시작
- limits 는 과도하게 높이지 않기

초보자용 기준:

- 처음에는 "작게 시작하고, 문제 생기면 늘린다"가 맞다.
- backend 는 Python/FastAPI 이므로 메모리를 너무 낮게 잡으면 응답이 불안정할 수 있다.

### 24.9 backend Service 와의 관계

Backend Deployment 는 직접 외부로 노출되지 않는다.

연결 흐름:

- backend Pod
- backend Service (`ClusterIP`)
- Ingress

초보자용 설명:

- Service 는 Pod 가 바뀌어도 같은 이름으로 접근하게 해준다.
- Ingress 는 외부 요청을 backend Service 로 넘긴다.

### 24.10 backend Deployment 의 주석 방향

실제 YAML 을 작성할 때는 다음처럼 주석을 달면 좋다.

- 왜 이 환경변수가 필요한지
- 이 probe 가 무엇을 확인하는지
- 이 서비스가 외부 공개인지 내부 전용인지
- 왜 replicas 를 1로 두는지

주석의 목표:

- 나중에 YAML 을 처음 보는 사람도 "왜 이렇게 썼는지" 바로 이해하게 만드는 것

### 24.11 backend 설계 체크리스트

- [ ] 운영 모드 uvicorn 사용
- [ ] `/api/health` probe 연결
- [ ] Secret 과 ConfigMap 분리
- [ ] postgres Service 이름과 DATABASE_URL 연결
- [ ] replicas 1로 시작
- [ ] 외부 노출은 Ingress 로만 처리

## 26. Frontend Deployment 설계 상세

Frontend 는 사용자가 직접 보는 화면을 담당한다. 이 프로젝트에서는 Next.js 가 frontend 역할을 한다.

### 26.1 frontend Deployment 의 역할

Frontend Deployment 는 다음 일을 한다.

- 브라우저에 화면을 제공한다.
- dashboard, documents, employees, schedules 같은 페이지를 보여준다.
- backend API 를 같은 호스트의 `/api` 경로로 호출한다.

### 26.2 운영 실행 명령

현재 frontend Dockerfile 은 개발용 실행 방식에 가깝다. Kubernetes 운영 배포에서는 다음 순서를 쓰는 것이 더 적절하다.

```text
npm run build
npm run start
```

설계 메모:

- 개발용 `npm run dev` 는 사용하지 않는다.
- 운영 배포는 빌드 후 정적/서버 실행 방식이 더 안정적이다.
- Pod 내부에서는 항상 3000 포트를 사용한다고 생각하면 된다.

### 26.3 frontend Deployment 에 들어갈 핵심 항목

포함할 내용:

- 이미지 이름
- replicas
- 컨테이너 포트 3000
- 환경변수 주입
- readinessProbe
- 리소스 요청/제한

### 26.4 frontend 가 사용하는 환경변수

Frontend 는 backend 보다 훨씬 단순하다.

주요 값:

- `NEXT_PUBLIC_API_URL`

설계 메모:

- 이 값은 브라우저에서 접근 가능한 값이다.
- 따라서 Secret 이 아니라 ConfigMap 에 둔다.
- 실제 값은 `http://<ingress-external-ip>/api` 또는 도메인 기반 주소가 된다.

### 26.5 readinessProbe 설계

Frontend 는 backend 처럼 DB 상태를 확인할 필요는 없다.

권장 방식:

- HTTP GET `/`

설계 이유:

- 메인 페이지가 응답하면 기본적으로 정상 동작으로 볼 수 있다.
- frontend 는 백엔드 연결 실패와 화면 서버 실패를 구분해서 볼 수 있다.

초보자용 설명:

- readiness 는 "화면을 보여줄 준비가 되었는가"를 본다.

### 26.6 livenessProbe 여부

초기 설계에서는 frontend 에도 livenessProbe 를 둘 수 있다.

다만 초보자용 1차 구현에서는 readinessProbe 만 두고 시작해도 된다.

권장 판단 기준:

- 처음에는 단순하게
- 나중에 불안정성이 보이면 livenessProbe 추가

### 26.7 replicas 설정

1차 구현에서는 replicas 를 1개로 시작한다.

이유:

- 초기에는 화면이 뜨는지 확인이 우선이다.
- 여러 Pod 를 띄워도 세션 상태를 따로 다루는 구조가 아직 없다.

### 26.8 리소스 요청/제한

frontend 는 Node.js 기반이라 메모리 사용량이 backend 와 다르게 보일 수 있다.

초보자용 기준:

- build 시점과 run 시점의 자원 사용을 구분해서 본다.
- 처음에는 너무 낮게 잡지 않는다.

### 26.9 frontend Service 와의 관계

Frontend Deployment 도 직접 외부로 노출하지 않는다.

연결 흐름:

- frontend Pod
- frontend Service (`ClusterIP`)
- Ingress

초보자용 설명:

- Service 는 frontend Pod 가 바뀌어도 같은 이름으로 접근하게 해준다.
- Ingress 는 `/` 요청을 frontend Service 로 보낸다.

### 26.10 frontend 설계 체크리스트

- [ ] 운영 모드 build/start 사용
- [ ] `NEXT_PUBLIC_API_URL` 은 ConfigMap 에서 주입
- [ ] Service 타입은 ClusterIP
- [ ] 외부 공개는 Ingress 로만 처리
- [ ] 1차 구현에서는 replicas 1로 시작

## 27. Ingress 설계 상세

Ingress 는 외부 사용자가 클러스터 안쪽의 서비스로 들어오는 문지기 역할을 한다.

### 27.1 Ingress 의 역할

이 프로젝트에서 Ingress 는 다음을 담당한다.

- 외부 접속을 한 곳으로 모은다.
- `/` 요청을 frontend 로 보낸다.
- `/api` 요청을 backend 로 보낸다.
- 나중에 도메인이 생기면 host 기반 라우팅도 처리한다.

### 27.2 Ingress Controller 와 Ingress 의 차이

초보자 기준으로 구분하면 다음과 같다.

- Ingress Controller: 실제로 트래픽을 처리하는 프로그램
- Ingress: 어떤 요청을 어디로 보낼지 적어둔 규칙 파일

이 프로젝트에서는 `ingress-nginx` 를 Ingress Controller 로 사용하는 것을 전제로 한다.

### 27.3 권장 경로 규칙

가장 단순한 구조는 아래와 같다.

- `/` → frontend Service
- `/api` → backend Service

설계 메모:

- 프론트는 화면 전용이다.
- 백엔드는 API 전용이다.
- 경로만 보고도 역할이 바로 보이도록 한다.

### 27.4 host 설계

1차 구현에서는 host 를 미리 고정해도 좋고, IP 기반으로 시작해도 된다.

추천 방식:

- 로컬 VM 단계에서는 `manufacturing.local` 같은 이름을 쓸 수 있다.
- 아직 도메인이 없으면 IP 기반으로 시작해도 된다.

초보자용 기준:

- 처음에는 "동작 확인"이 우선이다.
- 나중에 DNS 를 붙여도 Ingress 구조는 유지된다.

### 27.5 path rewrite 여부

이번 설계에서는 **rewrite 를 하지 않는 것**을 권장한다.

이유:

- 프론트 호출 경로가 `/api/...` 이다.
- backend 라우터도 `/api` prefix 를 사용한다.
- 경로를 바꾸지 않으면 구조가 가장 단순하다.

### 27.6 Ingress 에 들어갈 핵심 항목

포함할 내용:

- host
- path 규칙
- backend service 이름
- backend service port
- frontend service 이름
- frontend service port

### 27.7 MetalLB 와 Ingress 의 관계

로컬 3대 VM 클러스터에서는 MetalLB 가 Ingress Controller 의 외부 IP 를 제공한다.

흐름:

- MetalLB가 LoadBalancer IP 배정
- ingress-nginx Service 가 외부 IP 확보
- 사용자가 그 IP 로 접속
- Ingress 규칙에 따라 frontend/backend 로 전달

### 27.8 Ingress 설계 체크리스트

- [ ] ingress-nginx 설치 전제
- [ ] MetalLB 외부 IP 확보 전제
- [ ] `/` 와 `/api` 경로 분리
- [ ] rewrite 는 사용하지 않음
- [ ] frontend/backend Service 이름 고정

## 31. 모니터링 스택 전환 결정 (쿠버 네이티브)

이번 프로젝트의 모니터링은 Docker Compose 기반 구성(cAdvisor + docker 라벨 쿼리)을 그대로 옮기지 않고, Kubernetes 네이티브 관측 방식으로 전환한다.

### 31.1 최종 결정

- 독립 cAdvisor 컨테이너를 기본 스택에서 제외한다.
- 독립 nginx-exporter를 기본 스택에서 제외한다.
- 기본 수집기는 아래 4개를 사용한다.
  - Prometheus
  - backend `/metrics`
  - postgres-exporter
  - node-exporter + kube-state-metrics
- ingress-nginx 메트릭은 2차로 추가한다.
- Docker Compose 전용 라벨(`container_label_com_docker_compose_service`) 기반 쿼리는 신규 대시보드에서 사용하지 않는다.

### 31.2 결정 이유

- Kubernetes에서는 Pod/Node/Workload 중심 메트릭이 운영 문제를 더 정확히 보여준다.
- Compose 라벨 기반 쿼리는 K8s에서 재사용성이 낮고 이식성이 떨어진다.
- 운영 중 장애 분석은 `container` 단위보다 `deployment`, `pod`, `node` 축으로 보는 편이 빠르다.

```text
node-exporter ─────┤
kube-state-metrics ┘

ingress-nginx metrics (옵션, 2차)
```

- 한 대시보드에서 SQL과 Prometheus를 혼합할 수는 있지만, 패널 단위 책임은 분리한다.
